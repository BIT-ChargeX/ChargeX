# 每日协作流程说明（第8组）

> 适用：所有参与 GitHub 协作的组员，不分具体模块。每人每天照此执行即可。
> 仓库：https://github.com/BIT-ChargeX/ChargeX （分支 main，main 仅允许 PR 合并，无需 approve）

---

## 0. 每天开始前的总原则

- main 是唯一真源：**谁也不直接改 main**，一律「分支 → push → PR → Merge」。
- 一次一个功能点 = 一个分支 = 一次提交/一个 PR（尽量小，好评审、好回滚）。
- 动手前、动手前、动手前 **都先 pull 最新 main**，避免基于旧代码开发。
- 禁止 `git push -f`；冲突不要怕，先 pull 再合并。

---

## 1. 早上开工（每天固定动作）

```bash
cd <你的本地工作目录>/charging_plantform

# 切到 main 并拉到最新（别人昨晚/上午合进来的改动）
git checkout main
git pull origin main

# 为今天要做的功能点建一条分支（示例：做“附近充电站查询”）
git checkout -b feature/02-nearby
```

分支命名规范：`feature/<需求序号>-<英文短名>`，例如 `feature/01-login`、`feature/09-reserve`。

---

## 2. 开发中

- 只改**与当前功能点相关**的文件；动别人模块/公共文件前先在群里说一声。
- 代码风格与本工程一致：命令码写在 `ApiDefs.h`，客户端收发走 `NetClient`，服务端业务放对应 `service/*`，别在页面里写 SQL。
- 每完成一个“可编译的小节点”，就提交一次，提交信息格式：
  `[需求XX] 完成了什么`
  示例：`[需求09] 完成充电预约校验并锁定电桩`
- 提交三步：
  ```bash
  git add 具体文件              # 只提交本次相关的文件，别 git add -A 乱带
  git commit -m "[需求09] 完成充电预约校验并锁定电桩"
  ```

---

## 3. 本地自测（提交/合入前必做）

- 你改的工程必须能编译通过：
  ```bash
  cd server && qmake6 ChargingServer.pro && make -j2      # 按你改的工程替换
  ```
  或直接在 Qt Creator 里对你负责的工程跑一次构建。
- 涉及接口改动：至少用一次真实请求验证（启动服务器 + 对应客户端走一遍）。
- **改完服务端接口时，必须同步检查两侧命令码一致**（`server/src/common/ApiDefs.h` 与 `admin|client/src/common/ApiDefs.h`）。

---

## 4. 合并最新 main 到你的分支（防止冲突变大）

开发期间别人可能又合了 main，推之前先合一次：

```bash
git fetch origin
git merge origin/main      # 或 git rebase origin/main
# 若提示冲突：见第 6 节
git push origin feature/02-nearby
```

---

## 5. 收尾：推送 + 开 PR + 合并

```bash
git push origin feature/02-nearby
```

然后到 GitHub 网页（或用命令 `gh pr create`）：

1. 仓库首页会提示 **Compare & pull request**；
2. base 选 `main`，compare 选你的分支 `feature/02-nearby`；
3. Title/描述写清楚功能点；Create pull request；
4. 本仓库已配置 **无需 approve**，确认 Files changed 无误后直接 **Merge pull request**（建议用 Squash 合并保持 main 干净）；
5. 合并后删除已合入的分支（网页有 Delete branch 按钮）；
6. 回到本地，把 main 更新一下：
   ```bash
   git checkout main && git pull origin main
   ```

---

## 6. 遇到冲突怎么办（重要，但别慌）

冲突常见于“两人改了同一文件相近位置”。

```bash
git merge origin/main
# git 提示 CONFLICT (content): merge conflict in xxx.cpp
```

处理：
1. 打开冲突文件，找 `<<<<<<<` / `=======` / `>>>>>>>` 标记；
2. 保留双方要的代码（删除三个标记行）；
3. 保存后：
   ```bash
   git add xxx.cpp
   git commit -m "解决与 main 的冲突"
   git push origin feature/02-nearby
   ```

> 提示：改完冲突一定要**重新编译一次**——即使 git 自动合并成功，也可能有“语义冲突”（签名/字段对不上）。

---

## 7. 每天下班前自检清单

- [ ] 今天的改动都在一个 feature 分支上，且已 push；
- [ ] 已开 PR 并 **合并进 main**（或 PR 已建好、说明清楚未完成原因）；
- [ ] 本地 main 已 `git pull` 到最新；
- [ ] 没遗留“只在我电脑上、别人拿不到”的关键代码；
- [ ] 如有 DB 字段/协议字段变更，已在群里 @协议维护人 更新文档后再合。

---

## 8. 分工纪律（防冲突的硬约定）

| 谁 | 主要改的区域 | 注意 |
|---|---|---|
| 用户端负责人 | `client/src/account|station_nav|charging` | 用户端命令归属 USER_*/STATION_*/ORDER_* |
| 管理端负责人 | `admin/src/pages` | 管理命令带 token，命令归属 ADMIN_*/PILE_*/SALES_* |
| 服务端负责人(整合) | `server/src/common`（分发/连接）、`server/src/service` | 分发表、连接框架由整合者合入 |
| 数据库/协议负责人 | `schema.sql`、协议文档、`server/src/common/DbManager` | **表结构和协议字段只能由他改**；别人只提变更申请 |
| 模拟桩端 piledev | `piledev/` | 与 server 的 PILE_DEV_* 命令对齐 |

通用：
- 同一公共文件不同分区（ApiDefs 注释分区、分发表各一行 else-if）→ 基本不冲突；
- 谁动公共文件，谁先在群里报备一句；
- 每个功能点独立分支，别把两件事塞进一个 PR。

---

## 9. 验收联调顺序（供每天检查整体是否正常）

1. 起 `server` → 确认监听 9000；
2. 起 `piledev` → 日志显示“绑定 N 台”，server 出现其连接；
3. admin 登录（admin/123456）→ 监控页、实时运行日志页、各管理页正常刷新；
4. client 登录（11 位手机号）→ 找桩 → 预约 → 下单 → 结算链路通。

---

> **① 动手前 pull；② 功能写在自己的分支上、push 后走 PR；③ main 谁也不能直推。**
